  素のLLMは講座の情報を持っていないので、ここは第3回で用語集を検索させて直す。

- 表示できたトークン数（入力 / 出力）：`[tokens] 入力 21 / 出力 752 / 合計 773`

`app/ask.py` の `TODO(第1回 演習)` は `read_usage()` に置き換えた。

## 宿題

- 取り組んだレベル：**発展**（基礎・実装も合わせて実施）

### やったこと

**基礎：** モデルと temperature を変えて同じ質問を繰り返し、回答の違いを見た。
`--model` と `-t/--temperature` を `app/ask.py` に足した。temperature は未指定なら
`config` 自体を渡さず、モデルの既定値に任せる（「指定しない」と「0 を指定する」は別物なので）。

**実装：** `--chat` で会話履歴を保ったまま続けて質問できるようにした。

LLM 側は前のやり取りを覚えていない。`app/ask.py` の `chat()` は
`[user, model, user, model, ...]` という `types.Content` のリストを持っておき、
毎回その全部を送り直している。続いているように見えるのは、こちらが毎回
過去ログを送っているから。だから往復を重ねるほど入力トークンが増える。
`--chat` の各行に往復数を出しているのは、それが実際に効いているのを見るため。

細かいところ:

- `:reset` で履歴を消せる。長くなったとき入力トークンを切り詰めるのに要る。
- API エラーのときは、直前に `append` した user の発言を `pop()` で戻す。
  戻さないと履歴の user が2連続になり、次の送信で形が崩れる。

**発展：** `scripts/benchmark.py` で応答時間とトークン数を測った。

- モデル × 質問 × 試行回数 で総当たりし、1回ごとに `time.perf_counter()` で実時間を測る。
- 質問は性質の違う3つ。応答時間はほぼ出力の長さで決まるので、短い質問だけで比べると
  モデルの速さを見誤る。
  - `short` … 「LoRAとは何ですか？一文で答えてください。」（入力14tok）
  - `long` … 「LoRAの仕組みを、全結合層の重み行列の分解から順に…」（入力27tok）
  - `course` … 講座に固有の質問（入力21tok）
- 速さの指標は応答時間の中央値と「出力トークン毎秒」の2つ。後者には thought トークンも足している。
  思考モデルは出力が短くても裏でトークンを生成していて、その時間は応答時間に乗るため。
- 平均ではなく中央値を使った。実際に外れ値が出た（後述）。
- 失敗した回は平均に混ぜず、成功数（`3/3` のような形）と一緒に表に出す。
  レート制限で落ちた回を 0 秒として平均すると、速く見えてしまう。

測り直し:

```bash
uv run python -m scripts.benchmark --trials 3 --per-question
uv run python -m scripts.benchmark --from results/lec01-bench.json --per-question
```

### 考察

**1. 遅さの正体は思考トークンだった**

`gemini-3.5-flash` は中央値 11.22 秒で、lite 系（3.04 / 3.31 秒）の **3.4〜3.7倍遅い**。
ただし生成速度が遅いわけではない。出力トークン毎秒は 170.1 で、`3.1-flash-lite` の 93.8 より速い。

遅い理由は思考トークンにある。flash だけ平均 974 トークンを思考に使っていて、
lite 系は両方とも 0 だった。答えには出てこないが、生成はしているので時間に乗る。

一番はっきり出たのが `short`（「一文で答えてください」）で、

- 出力 **57** トークン / 思考 **364** トークン → 思考が答えの **6.4倍**
- 答えは一文なのに 3.11 秒かかる（lite は 0.98 秒）

「一文で」と指示しても、短くなるのは答えだけで、考える量は減らなかった。
短い答えが欲しいときに思考モデルを使うと、待ち時間だけ払って見返りが無い。

**2. 出力トークン毎秒は、出力が短いと使えない指標**

`short` の列だけ数値が崩れている（11.9 / 49.8 / 139.6）。
`long` では 125.2 / 212.9 / 182.1 なので、同じモデルでも 10 倍近く違う。

接続と最初の1トークンが出るまでの固定の待ち時間が、
出力 42 トークンのような短い応答では支配的になるため。
つまりこの指標は長い出力でしか意味を持たない。
指標を1つに絞らず、中央値と併記しておいて正解だった。

**3. 中央値にした判断は正しかった**

`3.1-flash-lite` の `short` は中央値 1.06 秒なのに、最大 8.92 秒。
`long` も 3.90 秒に対して最大 16.02 秒。3回中1回だけ飛び抜ける形。
平均だと `short` は 3.56 秒になり、実際の体感（ほぼ1秒）とかけ離れる。

一方 `3.5-flash-lite` は 0.76〜1.37、2.93〜3.04、5.14〜5.62 と全部安定していた。
同じ lite でも、ばらつきの大きさが違う。
**「速いモデル」を選ぶときは、中央値だけでなく最大値も見ないと危ない。**

**4. 入力トークンは誤差でしかない**

入力は 14〜27 トークンで、出力の 42〜1589 と比べると 2桁小さい。
この課題の範囲では、応答時間もトークン消費もほぼ全部が出力側で決まる。
ただし `--chat` では往復ごとに入力が積み上がるので、この前提は崩れる。

### レート制限との関係

**無料枠の制限は「1分あたりのリクエスト数」で、1リクエストの重さは見ていない。**
今回のデータだと、同じ1回でも中身がまるで違う。

| | 1リクエストの総トークン |
|---|---|
| `3.5-flash-lite` × `short` | 14 + 52 = **66** |
| `3.5-flash` × `long` | 27 + 1589 + 1402 = **3,018** |

**46倍の差があるのに、レート制限上はどちらも「1回」。**
つまり軽い質問を速いモデルに投げるほど、上限に早く当たる。逆説的だが、
**速いモデルほどレート制限で止まりやすい。**

実測値から1分あたり何回投げられるか計算すると（待機なしの場合）：

| モデル × 質問 | 1回の応答時間 | 理論上の RPM |
|---|---|---|
| `3.5-flash-lite` × `short` | 0.98s | 約 61 |
| `3.5-flash` × `long` | 17.27s | 約 3.5 |

無料枠の上限が 15 RPM 程度だとすると、**前者は確実に当たり、後者はどう頑張っても当たらない。**
今回 27 回投げて 1 度も止まらなかったのは、`--sleep 4.0` で待っていたから。
実際この設定だと最速の組み合わせでも約 12 RPM で、上限の手前に収まる。

ここから言えること：

- **応答時間を縮めても、総所要時間が縮むとは限らない。**
  `3.5-flash-lite` × `short` は 0.98 秒で終わるが、次を投げるまで 4 秒待つ。
  待ち時間の **80%** はモデルではなくレート制限が理由。
  この領域ではモデルを速くしても意味が無く、律速はレート制限側にある。
- **エージェント（第3回以降）はこの影響をまともに受ける。** 1つの質問で LLM を複数回呼ぶので、
  ユーザーから見て「1回質問した」だけでも、レート制限上は数回分を消費する。
  第1回より早く上限に達すると README にあるのは、この構造のため。
- 有料枠に移ると制限は RPM だけでなく TPM（1分あたりのトークン数）も効くので、
  そのときは上の「46倍の差」が無視できなくなる。無料枠と有料枠で、
  最適化すべき対象が変わる。

### 気づき・疑問

- 大きいモデルほど速く終わると思っていたが、逆だった。
  「性能が高い = 思考トークンを多く使う = 遅い」という関係があり、
  用途によっては lite の方が明確に良い。
  今回の `short` のように答えが短くて済む用途では、flash を選ぶ理由が無かった。
- 思考トークンは答えに出てこないのに課金とレート制限には効く。
  `usage_metadata` を見るまで存在に気づけない。表示するようにしておいて良かった。
- 疑問：`3.1-flash-lite` だけ外れ値が目立ったのは、モデルの性質なのか、
  旧バージョンでサーバー側の割り当てが薄いのか、たまたまなのかが分からない。
  試行回数 3 回では判断できないので、回数を増やすか時間帯を変えて測り直したい。
- 疑問：Codespaces の Southeast Asia リージョンから測っているので、
  ネットワークの往復時間が全部の数値に乗っている。
  `short` の 0.76 秒のうちどれだけがモデルの処理時間なのかは、この測り方では分けられない。
  ストリーミングで最初の1トークンが来るまでの時間を測れば切り分けられそう。
