### やったこと

**基礎：** モデルと temperature を変えて同じ質問を繰り返し、回答の違いを見た。
`--model` と `-t/--temperature` を `app/ask.py` に足した。temperature は未指定なら
`config` 自体を渡さず、モデルの既定値に任せる（「指定しない」と「0 を指定する」は別物なので）。

**実装：** `--chat` で会話履歴を保ったまま続けて質問できるようにした。

LLM 側は前のやり取りを覚えていない。`app/ask.py` の `chat()` は
`[user, model, user, model, ...]` という `types.Content` のリストを持っておき、
毎回その全部を送り直している。続いているように見えるのは、こちらが毎回
過去ログを送っているから。だから往復を重ねるほど入力トークンが増える。
`--chat` の各行に往復数を出しているのは、それが実際に効いているのを見るため。

細かいところ:

- `:reset` で履歴を消せる。長くなったとき入力トークンを切り詰めるのに要る。
- API エラーのときは、直前に `append` した user の発言を `pop()` で戻す。
  戻さないと履歴の user が2連続になり、次の送信で形が崩れる。

**発展：** `scripts/benchmark.py` で応答時間とトークン数を測った。

- モデル × 質問 × 試行回数 で総当たりし、1回ごとに `time.perf_counter()` で実時間を測る。
- 質問は性質の違う3つ（`short` / `long` / `course`）。応答時間はほぼ出力の長さで決まるので、
  短い質問だけで比べるとモデルの速さを見誤る。
- 速さの指標は応答時間の中央値と「出力トークン毎秒」の2つ。後者には thought トークンも足している。
  思考モデルは出力が短くても裏でトークンを生成していて、その時間は応答時間に乗るため。
- 平均ではなく中央値を使った。無料枠だとたまに極端に遅い回が混ざるので。
- 失敗した回は平均に混ぜず、成功数（`3/3` のような形）と一緒に表に出す。
  レート制限で落ちた回を 0 秒として平均すると、速く見えてしまう。

測り直し:

```bash
uv run python -m scripts.benchmark --trials 3            # 測って results/ に保存
uv run python -m scripts.benchmark --from results/lec01-bench.json --per-question
```

### レート制限との関係

（★ 実測後に、以下の観点で書く）

- 無料枠は「1分あたりのリクエスト数」で制限される。1リクエストの重さは見ていない。
  なので、短い質問を速いモデルに連投するほど上限に先に当たる。
  `--sleep` で1回ごとに待っているのはこのため。
- エージェント（第3回以降）は1つの質問で LLM を複数回呼ぶので、同じ体感の使い方でも
  第1回より早く上限に達する。
- 「速いモデルを選ぶ」と「上限に当たらない」は別の話になる。応答時間を詰めても、
  1分あたりのリクエスト数が変わらなければ、待ち時間は結局レート制限で決まる。
